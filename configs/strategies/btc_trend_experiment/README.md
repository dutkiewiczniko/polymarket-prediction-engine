# btc_trend_experiment — macro BTC trend followers

Strategies that condition on how BTC moved over long lookback periods (1h /
12h / 24h / 7d) *ending at market start*, then trade the side BTC is moving
towards:

- **open entry** — small buy (10% of effective balance) while the favored side
  is still near 50c in the first 90s of the market
- **cheap adds** — up to 40% of effective balance in 8% clips whenever the
  favored side dips to <= 0.35 with >= 45s left
- **take profit** — sell any position at 0.95

Configs are generated by `scripts/simulation/generate_btc_trend_configs.py`
(edit that, not the YAMLs).

## Data dependency

These configs read per-market columns `btc_change_{1h,12h,24h,7d}_pct`, which
must be added to the market CSVs first:

```
python scripts/data/enrich_markets_with_btc_trend.py --markets-folder <folder>
```

(Enrichment fetches public Binance 5m klines, no API key; cached in
`data/btc_price_history_5m.csv`. `simulator_ready_markets_liquidity_all_20260519`
was enriched 2026-07-09; original files backed up in
`archive/simulator_ready_markets_liquidity_all_20260519_pre_btc_trend.zip`.)

Running one of these configs on a non-enriched market CSV fails loudly with
`Unknown rule metric: 'btc_change_..._pct'`.

**LIVE-ENGINE GAP:** `scripts/live/live_strategy_suite.py` only puts orderbook
depth columns into `tick.extra` (see `build_tick`), so these configs will crash
live. Before going live, the live suite must compute the trend values from
Binance klines at each market start and add them to every tick's `extra`.

## Calibration (2026-07-09, 320-market bench 2026-05-16..18)

From `scripts/analysis/analyze_btc_trend_predictiveness.py`:

- Base rate on this window: down wins 63.7%.
- "Strong" thresholds = median |change| per period: 1h 0.2, 12h 1.0, 24h 1.5, 7d 5.0.
- **1h trend is noise** for the next 5 minutes (50.0% sign alignment, 52.5%
  even in the strongest quartile).
- **The whole window is one macro downtrend**: 24h and 7d changes are negative
  for ALL 320 markets, so their 63.7% "alignment" is exactly the down base
  rate. On this bench, long-period trend following is structurally
  down-bias-with-a-filter; `struct_down_unconditional.yaml` (identical
  structure, no trend condition, down only) is the control that isolates
  whether the filter adds anything. A genuine test of trend *direction*
  switching needs a market window containing an up-regime.
- Weak hint of mean reversion at trend extremes (strongest 24h/7d quartiles
  have the LOWEST down-win rates, 56%/55% vs 70% for the weakest), ~1 s.e.,
  unproven.
- The trend-favored side dips cheap in most markets (median min price
  0.12-0.26 with >30s left), so the <= 0.35 cheap-add threshold has plenty of
  fills.

## Results (6x30, offset 0, leaderboard bench conditions, 2026-07-09)

`runs/compare/btc_trend_6x30/`. Median / mean of 6 group rewards:

| config | median | mean | orders |
|---|---|---|---|
| struct_down_unconditional (control) | **69.1** | **93.0** | 807 |
| trend_12h | 6.5 | 37.1 | 525 |
| trend_24h | 3.0 | 16.6 | 198 |
| trend_24h_cheap_only | 5.4 | 14.5 | 159 |
| trend_12h_24h_confirm | 3.0 | 12.5 | 179 |
| trend_7d | 0.0 | 6.0 | 236 |

**Verdict: the trend filter strictly hurts.** Every filtered variant
underperforms the identical unconditional structure — the filter mostly
removes profitable trading time (whole groups go to zero), and per the
calibration the strongest-trend markets are the *worst* for trend-direction
(mean reversion at extremes). All variants are also far below the momentum
champion (887 median). Standalone macro-trend following is falsified on this
bench. Surviving uses for the btc_change columns: (a) an *inverse* filter
(trade down-bias hardest when the trend is weak/moderate, stand down at
extremes), (b) trend as a sizing overlay on momentum strategies, (c) regime
switching — none tested yet, and any test of direction-switching still needs
an up-regime market window.
